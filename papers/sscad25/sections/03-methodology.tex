\section{Memory-Aware Chunking Methodology}
\label{sec:methodology}

This section presents our memory-aware chunking approach, which leverages predictive modeling to determine optimal chunk sizes that balance computational efficiency with memory constraints.

\subsection{Theoretical Foundation}

\subsubsection{Memory Consumption Model}

We model the memory consumption of tensor operations as:

\begin{equation}
M(V) = \alpha \cdot V + \beta \cdot f(V) + \gamma
\end{equation}

where:
\begin{itemize}
    \item $M(V)$ is the peak memory usage for volume $V$
    \item $\alpha$ represents the base memory coefficient for input data
    \item $\beta \cdot f(V)$ captures operator-specific memory expansions
    \item $\gamma$ accounts for framework overhead and constants
\end{itemize}

For most tensor operations, $f(V) = V$, yielding a linear relationship.
However, some operators exhibit non-linear patterns due to algorithmic complexity or intermediate data structures.

\subsubsection{Optimal Chunking Problem}

Given a total volume $V_{total}$ and memory limit $M_{limit}$ per worker, the optimal chunking problem seeks to:

\begin{equation}
\begin{aligned}
\text{maximize} \quad & c \\
\text{subject to} \quad & M(c^3) \leq M_{limit} \cdot s \\
& V_{total} \mod c^3 = 0 \\
& c \geq c_{min}
\end{aligned}
\end{equation}

where $c$ is the chunk dimension, $s$ is the safety factor, and $c_{min}$ is the minimum viable chunk size.

This formulation balances competing objectives:
\begin{itemize}
    \item Larger chunks reduce scheduling overhead
    \item Memory constraints limit maximum chunk size
    \item Divisibility ensures even workload distribution
\end{itemize}

\subsection{Overview}

Memory-aware chunking addresses the limitations of heuristic-based methods by employing a predictive model to anticipate memory consumption based on input data shapes and operator-specific characteristics.
The core objective is to ensure memory usage remains consistently below a user-defined threshold while maximizing chunk sizes to minimize scheduling overhead.

\subsection{Predictive Memory Model}

Our approach relies on a regression model trained to predict peak memory consumption for tensor-based operations.
The model takes as input:

\begin{itemize}
    \item \textbf{Volume dimensions}: The shape of the input data (e.g., inlines × xlines × samples for seismic data)
    \item \textbf{Operator characteristics}: Specific properties of the computational kernel being applied
    \item \textbf{Data type}: The precision and type of numerical representation
\end{itemize}

The model is trained on profiling data collected from representative workloads, capturing the relationship between input characteristics and memory requirements including intermediate expansions.
We employ polynomial features to capture non-linear scaling patterns common in tensor operations.

\subsection{Chunk Size Determination Algorithm}

Algorithm~\ref{alg:memaware} presents our memory-aware chunking procedure.
The algorithm consists of four main steps:

\begin{algorithm}[ht]
\caption{Memory-Aware Chunking}
\label{alg:memaware}
\begin{algorithmic}[1]
\REQUIRE Volume dimensions $V = [d_1, d_2, d_3]$, memory limit $M$, safety factor $s$, predictive model $\mathcal{M}$
\ENSURE Optimal chunk dimension $c$
\STATE $\text{total\_memory} \gets \mathcal{M}.\text{predict}(V)$
\STATE $\text{memory\_per\_voxel} \gets \text{total\_memory} / \prod_{i=1}^{3} d_i$
\STATE $c \gets \lfloor \sqrt[3]{\frac{M \times s}{\text{memory\_per\_voxel}}} \rfloor$
\WHILE{$\exists i : d_i \bmod c \neq 0$ AND $c > \text{min\_size}$}
    \STATE $c \gets c - 1$
\ENDWHILE
\RETURN $c$
\end{algorithmic}
\end{algorithm}

\subsubsection{Memory Prediction}
The trained model estimates total memory consumption for processing the entire dataset volume.
This prediction integrates knowledge acquired through training on historical data, considering both volume dimensions and computational operator complexity.

\subsubsection{Per-Voxel Cost Calculation}
The algorithm translates predicted total memory consumption into a per-voxel memory cost by dividing by the total number of voxels.
This normalization enables consistent chunk sizing across different volume dimensions.

\subsubsection{Initial Chunk Dimension}
Using the per-voxel cost, we calculate an initial chunk dimension $c$ that satisfies:
\begin{equation}
c^3 \times \text{memory\_per\_voxel} \leq M \times s
\end{equation}
where $M$ is the memory limit and $s$ is a safety factor (typically 0.8) providing operational buffer space.

\subsubsection{Dimension Refinement}
The initial dimension is refined to ensure each volume dimension is evenly divisible by $c$, guaranteeing regular, rectangular sub-volumes.
This step prevents edge cases and ensures compatibility with distributed processing requirements.

\subsection{Comparison with Dask Auto-Chunking}

To contextualize our approach, we compare it with Dask's default auto-chunking mechanism.
Algorithm~\ref{alg:dask-auto} shows the simplified Dask heuristic:

\begin{algorithm}[ht]
\caption{Dask Auto-Chunking Heuristic}
\label{alg:dask-auto}
\begin{algorithmic}[1]
\REQUIRE Array dimensions $D = [d_1, d_2, ..., d_n]$, element size $e$, target size $T$
\ENSURE Chunk shape $C$
\STATE $\text{total\_bytes} \gets \prod_{i=1}^{n} d_i \times e$
\STATE $\text{num\_chunks} \gets \lceil \text{total\_bytes} / T \rceil$
\STATE $C[1] \gets \lceil d_1 / \text{num\_chunks} \rceil$
\FOR{$i = 2$ to $n$}
    \STATE $C[i] \gets d_i$ \COMMENT{Keep full size for other dimensions}
\ENDFOR
\RETURN $C$
\end{algorithmic}
\end{algorithm}

The key limitations of Dask's approach include:
\begin{itemize}
    \item No consideration of operator-specific memory patterns
    \item Chunking only along the first dimension, potentially creating inefficient shapes
    \item Inability to account for intermediate memory expansions
    \item Fixed target size regardless of available memory or workload characteristics
\end{itemize}

\subsection{Integration with Distributed Execution}

Our memory-aware chunking integrates seamlessly with Dask's distributed execution model.
When a computation is submitted:

\begin{enumerate}
    \item The input volume shape is analyzed
    \item The predictive model estimates memory requirements
    \item Optimal chunk dimensions are calculated based on available worker memory
    \item The data is partitioned according to these dimensions
    \item Tasks are distributed to workers with guaranteed memory safety
\end{enumerate}

This integration requires minimal changes to existing workflows while providing substantial improvements in reliability and resource utilization.

\subsubsection{Runtime Integration}

The memory-aware chunking mechanism integrates with Dask through a custom chunking function that:

\begin{lstlisting}[language=Python, caption={Memory-aware chunking implementation}]
def memory_aware_chunk(array, memory_limit_gb, safety_factor=0.8):
    # Load pre-trained model
    model = load_model(f"{operator_name}.pkl")
    
    # Predict memory for full volume
    volume_shape = array.shape
    predicted_memory = model.predict([volume_shape])
    
    # Calculate per-voxel memory cost
    total_voxels = np.prod(volume_shape)
    memory_per_voxel = predicted_memory / total_voxels
    
    # Determine chunk dimension
    available_memory = memory_limit_gb * safety_factor * 1e9
    chunk_voxels = available_memory / memory_per_voxel
    chunk_dim = int(np.cbrt(chunk_voxels))
    
    # Ensure divisibility
    while any(dim % chunk_dim != 0 for dim in volume_shape):
        chunk_dim -= 1
    
    return (chunk_dim, chunk_dim, chunk_dim)
\end{lstlisting}

\subsection{Complexity Analysis}

The computational complexity of memory-aware chunking consists of:

\begin{itemize}
    \item \textbf{Prediction}: $O(1)$ for linear models, $O(n)$ for tree-based models where $n$ is the number of trees
    \item \textbf{Chunk calculation}: $O(d)$ where $d$ is the maximum dimension size (for divisibility check)
    \item \textbf{Overall}: $O(d)$ dominated by the divisibility refinement step
\end{itemize}

This minimal overhead is negligible compared to the actual computation time of seismic operators, which typically scale as $O(V)$ or $O(V \log V)$ where $V$ is the volume size.

\subsection{Benefits and Trade-offs}

Memory-aware chunking offers several key benefits:

\begin{itemize}
    \item \textbf{Elimination of \ac{OOM} errors}: Automatic constraint enforcement ensures chunks remain within memory limits
    \item \textbf{Predictable scaling}: Systematic chunk selection enables even workload distribution
    \item \textbf{Reduced manual tuning}: Automated determination minimizes trial-and-error overhead
\end{itemize}

The primary trade-off is potentially increased execution time when the algorithm selects conservative chunk sizes.
However, as our experiments demonstrate, this overhead is often offset by improved reliability and the ability to handle larger datasets that would otherwise fail.
