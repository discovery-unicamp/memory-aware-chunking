\section{Experimental Results}
\label{sec:experimental-results}

This section presents a comprehensive evaluation of memory-aware chunking compared to Dask's auto-chunking and evenly-split strategies across various dataset sizes and worker configurations.

\subsection{Experimental Setup}

\subsubsection{Hardware Configuration}
All experiments were conducted on a single \ac{HPC} node equipped with an Intel Xeon Silver 4310 processor, 256 \ac{GB} \ac{RAM}, and two RTX A6000 \ac{GPU}s.
Despite \ac{GPU} availability, all runs used \ac{CPU} execution to ensure comparability across configurations.

\subsubsection{Datasets and Workloads}
We evaluated performance using synthetic seismic datasets with the gradient structure tensor (\ac{GST3D}) operator, a memory-intensive computation common in seismic analysis.
Dataset dimensions ranged from $100^3$ to $400^3$ voxels, covering small to large-scale workloads.
Each configuration was tested with 1, 2, 4, and 8 workers to assess scalability.

\subsubsection{Chunking Strategies}
We compared three strategies:
\begin{itemize}
    \item \textbf{Auto}: Dask's default heuristic-based chunking
    \item \textbf{Evenly-split}: Uniform division across workers
    \item \textbf{Memory-aware}: Our predictive model-based approach
\end{itemize}

\subsection{Trade-off Analysis}

Our results reveal a clear trade-off between execution speed and reliability:

\begin{itemize}
    \item \textbf{Small datasets ($\leq 100^3$)}: Auto or evenly-split chunking provides 5-10\% faster execution
    \item \textbf{Medium datasets ($200^3$)}: Memory-aware remains within 15\% of the fastest alternative while providing \ac{OOM} protection
    \item \textbf{Large datasets ($\geq 400^3$)}: Memory-aware is often the only viable option, especially with multiple workers
\end{itemize}

The median slowdown of memory-aware chunking when not the fastest option is 1.65×, a reasonable overhead for guaranteed reliability in production environments.

\subsection{Predictive Model Performance}

To understand the effectiveness of memory-aware chunking, it is essential to examine the underlying predictive model's performance.
Our approach relies on regression models trained to predict peak memory consumption based on input volume dimensions.

\subsubsection{Model Selection and Validation}

We evaluated nine regression models including Linear Regression, Polynomial Regression, Decision Tree, Random Forest, Gradient Boosting, XGBoost, Support Vector Regression, and Elastic Net.
The models were trained on profiling data from three seismic operators: Envelope, Gradient Structure Tensor (\ac{GST3D}), and Gaussian Filter.

Performance metrics revealed that simple linear models achieved near-perfect predictive power:
\begin{itemize}
    \item \textbf{Linear Regression}: $R^2 > 0.999$ for all operators
    \item \textbf{Elastic Net}: Comparable performance with slight regularization benefits
    \item \textbf{Complex models}: Negligible improvement despite increased computational cost
\end{itemize}

This finding supports the hypothesis that memory consumption scales linearly with input volume for tensor-based operations, enabling reliable predictions with minimal computational overhead.

\subsection{Scalability Analysis}

Beyond the basic performance metrics, we conducted detailed scalability analysis to understand how different chunking strategies behave under varying conditions.

\subsubsection{Worker Scaling Efficiency}

The scaling efficiency analysis demonstrates how each chunking mode performs as worker count increases.
Memory-aware chunking maintains near-linear scaling up to 8 workers, while auto-chunking and evenly-split strategies suffer from either OOM failures or excessive fragmentation at higher worker counts.

\subsubsection{Memory Overhead Analysis}

An important consideration in distributed computing is the memory overhead introduced by the framework itself.
Our measurements revealed:
\begin{itemize}
    \item \textbf{Base Dask overhead}: Approximately 500MB per worker
    \item \textbf{Task scheduling overhead}: 50-100MB depending on chunk count
    \item \textbf{Communication buffers}: Up to 200MB for inter-worker data transfer
\end{itemize}

Memory-aware chunking accounts for these overheads through its safety factor parameter, ensuring sufficient headroom for framework operations.

\subsubsection{Dynamic Runtime Monitoring}

Some systems monitor memory usage during execution and adjust dynamically.
While theoretically superior, this approach faces practical challenges:
\begin{itemize}
    \item \textbf{Reaction time}: Memory spikes occur faster than monitoring can respond
    \item \textbf{Overhead}: Continuous monitoring adds 5-10\% performance penalty
    \item \textbf{Complexity}: Requires sophisticated runtime infrastructure
\end{itemize}

Our predictive approach avoids these issues by making decisions before execution begins.

\subsection{Discussion}

The experimental results validate our approach's effectiveness in preventing OOM errors while maintaining competitive performance.
The key insights include:

\begin{enumerate}
    \item \textbf{Reliability vs. Speed}: Memory-aware chunking trades modest speed reduction for complete elimination of OOM failures
    \item \textbf{Scalability}: Our approach enables higher worker utilization for large datasets where conventional methods fail
    \item \textbf{Predictability}: Consistent memory usage patterns simplify capacity planning and resource allocation
    \item \textbf{Practical Impact}: For HPC environments with job queuing and limited time slots, avoiding OOM-induced restarts provides significant operational benefits
\end{enumerate}

These findings demonstrate that memory-aware chunking offers a robust solution for memory-constrained distributed computing, particularly valuable in production HPC environments where reliability is paramount.
