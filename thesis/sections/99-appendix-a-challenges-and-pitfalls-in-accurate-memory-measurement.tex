\section{Introduction}
\label{sec:appendix-introduction}

Accurate memory measurement in Python poses challenges, especially in scientific computing and \ac{HPC} contexts.
Resource allocation in these environments directly affects performance, scalability, and cost-effectiveness.
A clear understanding of application memory consumption supports decisions on efficient hardware allocation and uncovers potential inefficiencies in data handling or algorithmic structure.
Several aspects of Python's runtime behavior and external \ac{OS} optimizations create complications in the measurement process.

Python manages memory dynamically.
Its interpreter frequently allocates and deallocates memory through reference counting, enhanced by cyclical garbage collection.
These mechanisms do not always free memory immediately after object deletion.
Transient usage peaks often inflate measured consumption.
Libraries such as NumPy or TensorFlow can allocate memory outside Python's garbage collector, so purely Python-centric approaches do not capture the total footprint.
\ac{OS} factors, including \ac{COW}, memory compression (for example, zram~\cite{zram}), and caching optimizations, also obscure application-level usage.

Shared or interactive environments, such as Jupyter notebooks, can introduce challenges if lingering objects from prior executions persist in memory.
These artifacts bias results unless the user resets the environment or executes experiments in complete isolation.
Measurement tools introduce overhead and sometimes alter the memory usage patterns under investigation.
Researchers must carefully control data collection methodologies and application execution environments to ensure valid outcomes.


\section{Common Challenges and Pitfalls}
\label{sec:appendix-common-challenges}

\subsection{Dynamic Memory Allocation and Fragmentation}
\label{subsec:appendix-dynamic-allocation}

Python's dynamic allocation routines and internal memory manager create variability in memory usage.
Garbage collection runs periodically and does not always release memory to the \ac{OS} immediately when objects become unreferenced.
Python's memory allocator (\texttt{pymalloc}) can also cause internal fragmentation, leaving unoccupied memory regions allocated but unavailable to other processes.

Large allocations and deallocations in unpredictable sequences aggravate fragmentation.
\ac{HPC} and data analysis frequently generate massive arrays (often gigabytes in size) that undergo repeated creation and destruction.
Fragmentation accumulates in ways that inflate measured memory usage.

\subsection{Delayed Garbage Collection}
\label{subsec:appendix-delayed-gc}

Residual memory from previous workloads often persists if a Python process remains active.
Jupyter notebooks frequently exhibit this issue because repeated cell execution does not reload the interpreter.
Garbage collection triggers at non-deterministic intervals or when the application reaches allocation thresholds.
Code that logically frees memory might not immediately reduce system-level usage.

Later runs often show inflated usage if delayed deallocation carries over from earlier operations.
Spurious or exaggerated peaks emerge when experiments run back-to-back.
Strategies that account for garbage-collection timing or reset the environment help avoid these distortions.

\subsection{Operating System and Container-Level Effects}
\label{subsec:appendix-os-effects}

Modern \ac{OS} implementations rely on virtual memory to abstract physical RAM into continuous process-specific address spaces.
Features such as \ac{COW} postpone actual memory usage until processes perform writes.
Linux provides zswap~\cite{zswap} or zram~\cite{zram} to compress memory pages, complicating direct process-level usage measurements.

Containerization introduces another abstraction layer.
Docker or similar platforms effectively isolate processes, although memory usage reported inside a container can differ from measurements on the host.
Containers enforce caps that trigger \ac{OOM} termination if usage crosses set thresholds.
Containers also rely on the host kernel's memory management.
Cross-referencing container-level metrics with host-level data supplies a complete view.

\subsection{Caching Mechanisms and Reused Objects}
\label{subsec:appendix-caching}

Caching occurs at the Python interpreter and \ac{OS} levels.
Python caches small integers, certain strings, and recently deallocated blocks.
The \ac{OS} caches disk blocks in \ac{RAM}.
These caches improve performance but complicate memory measurement by adding unpredictable usage.

Third-party libraries, such as large-scale numeric frameworks, also manage internal buffers and caches.
These buffers might not appear in Python's built-in measurement routines.
Specialized profiling at the native layer often becomes necessary to track these additional allocations.

\subsection{Measurement Tool Overheads}
\label{subsec:appendix-measurement-tool-overheads}

Profilers that monitor memory usage add overhead.
Sampling-based approaches raise \ac{CPU} load by periodically querying memory states.
Allocation-tracking tools maintain their metadata in memory.
Overheads inflate measured usage or alter execution timing, affecting garbage collection.

Verifying results with multiple measurement strategies avoids misleading conclusions.
Comparisons between lightweight external monitors (for example, Docker metrics) and Python-based profilers (such as \texttt{tracemalloc}) can detect divergences caused by tool overhead.

Several strategies appear, including \ac{CPU} affinity, switching to the \texttt{vfs} storage driver, dropping page caches, and forcing garbage collection.
The objective is to find the most consistent performance across runs.
Initial experiments show that restarting containers alone does not remove first-run spikes from library loading, just-in-time compilation, and file-system caching.
Subsequent attempts demonstrate that combining \ac{CPU} affinity with cache drops eliminates those fluctuations.
Results show minimal variance in both memory usage and page faults.

\section{Summary}
\label{sec:appendix-issues-recommendations}

Memory measurement in Python frequently encounters hurdles caused by residual objects, library-level caching, dynamic allocation, and containerization effects.
Multiple aspects of the Python runtime complicate memory tracking.
Containers add another abstraction layer that influences reported usage.
External libraries often manage memory outside Python's standard garbage-collection model.
Some measurement tools only capture Python-level allocations, while others reveal container-wide or system-level usage.
Experimentation confirmed that first-run memory spikes often appear due to library loading and caching effects.
Pinning the container to a single \ac{CPU} core, dropping caches between runs, and forcing consistent environment settings eliminates these spikes.
Combining psutil, Docker metrics, and Python's resource module provides a broad, cross-validated view of memory usage.
Incremental memory-pressure experiments highlight a practical lower bound for successful algorithm execution, showing that usage near 5.3\ac{GB} is not an artifact.
Memory usage that falls below that mark often triggers \ac{OOM} or runtime errors.

Memory resources directly impact performance and cost in scientific computing and \ac{HPC} contexts.
Large-scale data processing demands robust measurement strategies to ensure adequate resource allocation.
Inflated usage metrics can distort results if experiments do not account for residual memory, delayed garbage collection, fragmentation, and caching.
Containers provide isolation benefits but introduce specific measurement challenges.
Therefore, experiments should employ multiple profiling tools, reset environments or containers before each run, and validate results under controlled memory constraints to approximate real-world scenarios closely.
Comparing Python-level metrics with container-level measurements clarifies the distribution of memory consumption among Python objects, external libraries, and system overhead.


\section{Conclusion}
\label{sec:appendix-conclusion}

Accurate memory measurement in Python relies on careful planning and validation.
Language-level features like dynamic allocation and garbage collection require methodical experiments to capture genuine peaks.
Containers and \ac{OS} optimizations add layers of abstraction that influence observed usage.
Synthetic seismic data experiments highlight the tendency for first-run spikes and demonstrate that environment isolation and cache drops enhance reproducibility.
Cross-verification through psutil, resource, and Docker's cgroup metrics reveals subtle differences due to scope and overhead.
Imposing memory limits and assessing failure thresholds establishes a real boundary for successful operation.
Results confirm that reliable peak measurements for memory-intensive tasks often hover around 5.3\ac{GB} in these seismic-envelope tests.
Controlling the environment, combining complementary measurement tools, and testing under memory constraints minimize errors and misinterpretations.
Future experiments on this thesis benefit from continuing these practices to ensure accurate resource forecasts and optimized system performance.
