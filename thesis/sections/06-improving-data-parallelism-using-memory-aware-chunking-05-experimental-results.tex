\section{Experimental Results}
\label{sec:idp-experimental-results}

This section presents a comprehensive evaluation of three chunking strategies employed within a Dask-based environment:
\begin{enumerate}
    \item \emph{Auto-chunking} relies on Dask's built-in heuristics to infer a best-fit chunk size.
    \item \emph{Evenly-split chunking}, wherein data is uniformly divided across workers.
    \item \emph{Memory-aware} (memaware) chunking, which leverages a predictive model of memory usage to allocate chunks in a manner that aims to mitigate \ac{OOM} errors.
\end{enumerate}
This experimental study aims to elucidate trade-offs regarding execution time, peak memory consumption, and \ac{OOM} frequency across various dataset shapes (small, medium, large) and under different worker configurations.
The results underscore how each chunking mode behaves under increasing workload sizes and concurrency levels, ultimately guiding best practices for users in both constrained and unconstrained memory scenarios.

\subsection{Overall Performance Comparison}
\label{subsec:overall-performance}

The first phase of the analysis holistically compares execution time and memory consumption for each chunking strategy.
It pools data from all tested shapes and worker counts.
The analysis focuses on runs completed under each approach (\ie no \ac{OOM} errors) for this comparison.
This approach ensures the inclusion of only configurations viable under all three chunking modes.

The primary performance metrics include:

\begin{itemize}
    \item \emph{Average execution time} (in seconds) --- Summarizes total runtime across successful runs.
    \item \emph{Median execution time} (in seconds) --- Provides a more robust measure of central tendency, mitigating the influence of extreme outliers.
    \item \emph{Average and median peak memory usage} (in bytes) --- Indicates typical peak memory utilization.
    \item \emph{Number of runs} --- Shows total executed trials (excluding any that ended prematurely due to memory issues).
\end{itemize}

Table~\ref{tab:mode_summary} presents a high-level view of the results for the three chunking modes.

\begin{table}[ht]
    \centering
    \caption{Summarized Execution Time and Peak Memory Usage by Chunking Mode (Successful Runs Only)}
    \label{tab:mode_summary}
    \begin{tabular}{lccc}
        \toprule
        \textbf{Mode} & \textbf{Time (avg/med, s)} & \textbf{Mem (avg/med, bytes)}             & \textbf{Runs} \\
        \midrule
        auto          & 19.7 / 15.7                & 3.20$\times 10^{9}$ / 2.62$\times 10^{9}$ & 525           \\
        evenly\_split & 19.5 / 15.7                & 3.20$\times 10^{9}$ / 2.63$\times 10^{9}$ & 525           \\
        memaware      & 32.4 / 28.1                & 1.53$\times 10^{9}$ / 1.24$\times 10^{9}$ & 525           \\
        \bottomrule
    \end{tabular}
\end{table}

\paragraph{Key Observations.}
\begin{itemize}

    \item \textbf{Auto-chunking and evenly-split modes exhibit similar speed and memory profiles.}
    Both approaches produce an average execution time of roughly 19-20\,s, with medians near 15.7\,s.
    They consume approximately 3.20\ac{GB} of memory at peak.
    Excluding configurations that triggered \ac{OOM} in either mode yields these performance numbers.

    \item \textbf{Memaware chunking runs more slowly but uses far less memory.}
    Its average runtime is 32.4\,s, with a median of 28.1\,s.
    The average and median peak memory consumption drop significantly to around 1.53\ac{GB} and 1.24\ac{GB}.

    \item \textbf{OOM considerations and dataset coverage.}
    This table includes only cases where all three modes succeeded.
    The memaware approach ran successfully in all 768 trials, while auto-chunking and evenly-split chunking encountered \ac{OOM} errors in 243 and 128 cases, respectively.
    This method preserves a balanced comparison.

\end{itemize}

Auto-chunking and evenly-split typically offer faster runtimes for moderately sized inputs, assuming sufficient memory availability.
Memaware chunking lowers peak memory footprints substantially and handles larger workloads without out-of-memory errors, but at the cost of longer execution times.

\subsection{Out-of-Memory Incidents}
\label{subsec:oom-results}

While average execution time is often the most visible performance metric, real-world applications must also consider stability and the potential for catastrophic memory overflows.
Table~\ref{tab:oom_stats} illustrates how frequently each chunking method triggered \ac{OOM} conditions (leading to worker failures or job terminations).

\begin{table}[ht]
    \centering
    \caption{\ac{OOM} Counts and Ratios by Chunking Mode}
    \label{tab:oom_stats}
    \begin{tabular}{lrrr}
        \toprule
        \textbf{Chunking Mode} & \textbf{\ac{OOM}s} & \textbf{Runs} & \textbf{\ac{OOM}-ratio} \\
        \midrule
        auto                   & 243                & 525           & 0.31                    \\
        evenly\_split          & 128                & 525           & 0.20                    \\
        memaware               & 0                  & 768           & 0.00                    \\
        \bottomrule
    \end{tabular}
\end{table}

\paragraph{Key Takeaways.}
\begin{itemize}
    \item \textbf{Auto-chunking exhibited the highest \ac{OOM} rate}: 243 out of 525 runs (a ratio of 0.31). These results suggest that Dask's heuristic chunk sizing could overshoot worker memory capacities in certain shapes and concurrency levels.
    \item \textbf{Evenly-split chunking was slightly more stable than auto-chunking}: with 128 out of 525 runs failing (\(\approx 8\%\)).
    \item \textbf{Memaware chunking had zero \ac{OOM} events in 768 runs}: These outcomes underscore how the more conservative, predictive memory model successfully capped memory usage below the thresholds that typically lead to worker crashes.
\end{itemize}

The absence of \ac{OOM}s in the memaware approach highlights its potential value for large-scale or memory-constrained scenarios.
Although it is slower, it can operate reliably at high worker counts, which might be pivotal in enterprise or scientific contexts where unpredictable failures are unacceptable.

\subsection{Performance Across Data Shapes}
\label{subsec:per-shape-performance}

To dig deeper, the analysis examines how each chunking strategy scales with increasingly complex data shapes.
The experiment considers three representative categories of shapes:
\begin{itemize}
    \item \textbf{Small datasets}: \eg, \(100 \times 100 \times 100\).
    \item \textbf{Medium datasets}: \eg, \(200 \times 200 \times 200\) or \(200 \times 200 \times 300\).
    \item \textbf{Large datasets}: \eg, \(400 \times 400 \times 300\).
\end{itemize}
Results from these categories provide a clear cross-section of how chunking modes perform when the problem size doubles or quadruples in one or more dimensions.

\paragraph{Small Shapes (\eg, \(100 \times 100 \times 100\).}
In these smaller volumetric datasets, auto-chunking and evenly-split chunking generally outperform memaware by a margin of about 5--10\%.
As shown later in Table~\ref{tab:leaderboard-100-100}, these methods benefit from low overhead when chunk sizes remain modest.

\paragraph{Medium Shapes (\eg, \(200 \times 200 \times 200\).}
When datasets grow to medium volumes, the performance gap narrows.
Auto-chunking and evenly-split remain competitive, but memaware typically stays within 5–15% of the fastest method.
Moreover, memaware achieves better memory utilization, safeguarding against potential \ac{OOM} errors when increasing concurrency.

\paragraph{Large Shapes (\eg, \(400 \times 400 \times 300\).}
As we escalate to large-scale data, memaware chunking often becomes the only viable approach at higher worker counts.
Auto and evenly-split either
\begin{itemize}
    \item hit severe memory bottlenecks leading to \ac{OOM}, or
    \item experience dramatic slow-downs (\eg, beyond 200\,s).
\end{itemize}
In contrast, memaware consistently completes runs in an acceptable time frame (often \< 60\,s for the tested shapes) while maintaining a \emph{zero} \ac{OOM} record.

\subsection{Discussion of Key Findings}
\label{subsec:discussion-of-results}

Based on the results across multiple shapes and concurrency levels, we draw the following key conclusions:

\begin{enumerate}
    \item \textbf{Auto vs.\ evenly-split chunking}. Both modes deliver near-identical performance for small-to-medium data where memory resources are not heavily constrained. Evenly-split chunking can be slightly more stable (fewer \ac{OOM}) and occasionally outperforms auto-chunking when data shapes match well with uniform splits.

    \item \textbf{Memaware chunking's advantage scales with data size}. At small volumes (\eg, \(100 \times 100 \times 100\)), memaware is roughly 5--10\% slower than the best alternative. This difference increases for "medium" volumes (5--15\%). However, once data shapes become large (\(400 \times 400 \times 300\)), memaware's relative reliability (0 \ac{OOM}s) and bounded memory usage become a decisive factor, especially at high worker counts.

    \item \textbf{Trade-offs in design constraints}. Users must balance:
    \begin{itemize}
        \item \emph{Speed of execution}---Auto-chunking or evenly-split chunking is superior if abundant RAM is guaranteed.
        \item \emph{Memory stability}---Memaware chunking ensures stability, can handle more aggressive parallelism, and helps avoid forced restarts due to out-of-memory incidents.
    \end{itemize}

    \item \textbf{Practical considerations for \ac{HPC} or cloud environments}.
    Many \ac{HPC} or cloud deployments allow horizontal scaling of ephemeral worker nodes.
    Memaware chunking reduces the risk of losing an entire cluster job due to memory exhaustion, which becomes critical in pay-per-use or short-time-slot \ac{HPC} queue systems where restarts incur significant costs.
\end{enumerate}

\subsection{Summary of Findings}
\label{subsec:summary-of-findings}

In summary, the experimental data yield four primary insights:

\begin{enumerate}

    \item \textbf{Overall Performance by Mode.}
    Auto-chunking and evenly-split chunking deliver near-identical results for smaller runs regarding both time and memory usage.
    Memaware is slower on average (median around 28.1s vs. 15.7s for auto/evenly-split), but cuts median memory usage by about 28\%.

    \item \textbf{Out-of-Memory Behavior.}
    Auto-chunking and evenly-split chunking both encounter non-negligible \ac{OOM} rates (0.31 vs.\ 0.20, respectively), whereas memaware exhibits zero \ac{OOM}s across 768 runs.

    \item \textbf{Per-Shape Leaderboard.}
    For small shapes, auto or evenly-split wins by a modest margin; for medium shapes, memaware remains close (5--15\% slower); and for large shapes, memaware is often the only method that completes with high concurrency.

    \item \textbf{Trade-offs and Recommendations.}
    Auto or evenly-split chunking offers the best speed for systems with ample RAM and smaller datasets.
    For stability, predictable memory usage, or reliably handling massive volumes, memaware chunking provides superior results, despite its slower runtime.

\end{enumerate}

These findings highlight the importance of carefully selecting a chunking strategy based on workload size and memory availability.
In environments where memory is scarce or the dataset is large and complex, the memaware approach offers a robust safeguard against \ac{OOM} while still delivering respectable throughput.
