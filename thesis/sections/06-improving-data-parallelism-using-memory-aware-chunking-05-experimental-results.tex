\section{Experimental Results}
\label{sec:idp-experimental-results}

This section presents a comprehensive evaluation of three chunking strategies employed within a Dask-based environment:
\begin{enumerate}
    \item \emph{Auto-chunking}, which relies on Dask's built-in heuristics to infer a best-fit chunk size.
    \item \emph{Evenly-split chunking}, wherein data is uniformly divided across workers.
    \item \emph{Memory-aware} (memaware) chunking, which leverages a predictive model of memory usage to allocate chunks in a manner that aims to mitigate \ac{OOM} errors.
\end{enumerate}
The goal of this experimental study is to elucidate trade-offs regarding execution time, peak memory consumption, and \ac{OOM} frequency across various dataset shapes (small, medium, large) and under different worker configurations.
The results underscore how each chunking mode behaves under increasing workload sizes and concurrency levels, ultimately guiding best practices for users in both constrained and unconstrained memory scenarios.

\subsection{Overall Performance Comparison}
\label{subsec:overall-performance}

The first phase of analysis contrasts the execution time and memory consumption for each chunking strategy in a holistic manner, pooling data from all tested shapes and worker counts.
The primary performance metrics considered include:
\begin{itemize}
    \item \emph{Average execution time} (in seconds) --- summarizing total runtime across all runs.
    \item \emph{Median execution time} (in seconds) --- providing a more robust measure of central tendency, mitigating the influence of extreme outliers.
    \item \emph{Average and median peak memory usage} (in bytes) --- gauging how much memory is typically utilized at peak load.
    \item \emph{Number of runs} --- total successful plus failed (if any runs ended prematurely).
\end{itemize}

Table~\ref{tab:mode_summary} presents a bird's-eye view of the results:

\begin{table}[ht]
    \centering
    \caption{Summarized Execution Time and Peak Memory Usage by Chunking Mode}
    \label{tab:mode_summary}
    \begin{tabular}{lccc}
        \toprule
        \textbf{Mode} & \textbf{Time (avg/med, s)} & \textbf{Mem (avg/med, bytes)}             & \textbf{Runs} \\
        \midrule
        auto          & 19.7 / 15.7                & $3.20\times 10^{9}$ / $2.62\times 10^{9}$ & 525           \\
        evenly\_split & 19.5 / 15.7                & $3.20\times 10^{9}$ / $2.63\times 10^{9}$ & 525           \\
        memaware      & 51.0 / 37.7                & $2.31\times 10^{9}$ / $1.89\times 10^{9}$ & 768           \\
        \bottomrule
    \end{tabular}
\end{table}

\paragraph{Key Observations.}
\begin{itemize}

    \item \textbf{Auto-chunking and evenly-split are nearly tied in raw speed.} Both methods showed average execution times around 19--20 seconds, with median values of approximately 15.7 seconds. Their average and median peak memory usage also hovered around 2.6--3.2\,GB, indicating fairly similar resource footprints for the tested suite of datasets.

    \item \textbf{Memaware chunking trades speed for reliability.} The average execution time for memaware rose to about 51 seconds, while its median time was around 37.7 seconds.
    However, this increased runtime coincided with a significantly lower peak memory usage: a median peak of about 1.89\,GB, reflecting a notable 28\% reduction compared to the other two methods.

\end{itemize}

These high-level results illustrate the essential trade-off: if raw throughput on moderate workloads is paramount and sufficient memory is available, the default or evenly-split chunking is appealing.
But if memory resources are constrained or the dataset grows large enough to risk \ac{OOM} errors, the memaware strategy helps stabilize the workload at the expense of lengthier runs.

\subsection{Out-of-Memory Incidents}
\label{subsec:oom-results}

While average execution time is often the most visible performance metric, real-world applications must also consider stability and the potential for catastrophic memory overflows.
Table~\ref{tab:oom_stats} illustrates how frequently each chunking method triggered \ac{OOM} conditions (leading to worker failures or job terminations).

\begin{table}[ht]
    \centering
    \caption{\ac{OOM} Counts and Ratios by Chunking Mode}
    \label{tab:oom_stats}
    \begin{tabular}{lrrr}
        \toprule
        \textbf{Chunking Mode} & \textbf{\ac{OOM}s} & \textbf{Count} & \textbf{\ac{OOM}-ratio} \\
        \midrule
        auto                   & 79                 & 525            & 0.15                    \\
        evenly\_split          & 42                 & 525            & 0.08                    \\
        memaware               & 0                  & 768            & 0.00                    \\
        \bottomrule
    \end{tabular}
\end{table}

\paragraph{Key Takeaways.}
\begin{itemize}
    \item \textbf{Auto-chunking exhibited the highest \ac{OOM} rate}: 79 out of 525 runs (a ratio of 0.15). This suggests that in certain shapes and concurrency levels, Dask's heuristic chunk sizing could overshoot worker memory capacities.
    \item \textbf{Evenly-split chunking was slightly more stable than auto-chunking}: with 42 out of 525 runs failing (\(\approx 8\%\)).
    \item \textbf{Memaware chunking had zero \ac{OOM} events in 768 runs}: This underscores how the more conservative, predictive memory model successfully capped memory usage below the thresholds that typically lead to worker crashes.
\end{itemize}

The absence of \ac{OOM}s in the memaware approach highlights its potential value for large-scale or memory-constrained scenarios.
Although it is slower, it can operate reliably at high worker counts, which might be pivotal in enterprise or scientific contexts where unpredictable failures are unacceptable.

\subsection{Performance Across Data Shapes}
\label{subsec:per-shape-performance}

To dig deeper, we examine how each chunking strategy scales with increasingly complex data shapes.
Three representative categories of shapes are considered:
\begin{itemize}
    \item \textbf{Small datasets}: \eg, \(100 \times 100 \times 100\).
    \item \textbf{Medium datasets}: \eg, \(200 \times 200 \times 200\) or \(200 \times 200 \times 300\).
    \item \textbf{Large datasets}: \eg, \(400 \times 400 \times 300\).
\end{itemize}
The results from these categories provide a good cross-section of how chunking modes perform when the problem size doubles or quadruples in one or more dimensions.

\paragraph{Small Shapes (\eg, 100\(\times\)100\(\times\)100).}
In these smaller volumetric datasets, both auto-chunking and evenly-split chunking generally outperform memaware by a margin of about 5--10\%.
As shown later in Table~\ref{tab:leaderboard-100x100}, these methods benefit from low overhead when chunk sizes remain modest.

\paragraph{Medium Shapes (\eg, 200\(\times\)200\(\times\)200).}
When the datasets grow to medium volumes, the performance gap narrows.
Auto-chunking and evenly-split remain competitive, but memaware is usually within 5--15\% of the fastest method.
Moreover, memaware continues to demonstrate better memory utilisation, safeguarding against potential \ac{OOM} errors when concurrency is increased.

\paragraph{Large Shapes (\eg, 400\(\times\)400\(\times\)300).}
As we escalate to large-scale data, memaware chunking often becomes the only viable approach at higher worker counts.
Auto and evenly-split either
\begin{itemize}
    \item hit severe memory bottlenecks leading to \ac{OOM}, or
    \item experience dramatic slow-downs (\eg, beyond 200\,s).
\end{itemize}
In contrast, memaware consistently completes runs in an acceptable time frame (often \< 60\,s for the tested shapes) while maintaining a \emph{zero} \ac{OOM} record.

\subsection{Discussion of Key Findings}
\label{subsec:discussion-of-results}

Based on the results across multiple shapes and concurrency levels, we draw the following key conclusions:

\begin{enumerate}
    \item \textbf{Auto vs.\ evenly-split chunking}. For small-to-medium data where memory resources are not heavily constrained, both modes deliver near-identical performance. Evenly-split chunking can be slightly more stable (fewer \ac{OOM}) and occasionally outperforms auto-chunking when data shapes match well with uniform splits.

    \item \textbf{Memaware chunking’s advantage scales with data size}. At small volumes (\eg, \(100 \times 100 \times 100\)), memaware is roughly 5--10\% slower than the best alternative. This difference increases for “medium” volumes (5--15\%), but once data shapes become large (\(400 \times 400 \times 300\)), memaware’s relative reliability (0 \ac{OOM}s) and bounded memory usage become a decisive factor, especially at high worker counts.

    \item \textbf{Trade-offs in design constraints}. Users must balance:
    \begin{itemize}
        \item \emph{Speed of execution}---Auto-chunking or evenly-split chunking is superior if abundant RAM is guaranteed.
        \item \emph{Memory stability}---Memaware chunking ensures the greatest stability, can handle more aggressive parallelism, and helps avoid forced restarts due to out-of-memory incidents.
    \end{itemize}

    \item \textbf{Practical considerations for \ac{HPC} or cloud environments}. In many \ac{HPC} or cloud deployments, ephemeral worker nodes can be scaled horizontally. Memaware chunking reduces the risk of losing an entire cluster job if memory is exhausted, which can be critical in pay-per-use or short-time-slot \ac{HPC} queue systems where restarts are expensive.
\end{enumerate}

\subsection{Summary of Findings}
\label{subsec:summary-of-findings}

In summary, the experimental data yields four primary insights:

\begin{enumerate}

    \item \textbf{Overall Performance by Mode.}
    Auto-chunking and evenly-split chunking deliver near-identical results in terms of both time and memory usage for smaller runs.
    Memaware is slower on average (median around 37.7s vs. 15.7s for auto/evenly-split), but cuts median memory usage by about 28\%.

    \item \textbf{Out-of-Memory Behavior.}
    Auto-chunking and evenly-split chunking both encounter non-negligible \ac{OOM} rates (0.15 vs.\ 0.08, respectively), whereas memaware exhibits zero \ac{OOM}s across 768 runs.

    \item \textbf{Per-Shape Leaderboard.}
    For small shapes, auto or evenly-split wins by a modest margin; for medium shapes, memaware remains close (5--15\% slower); and for large shapes, memaware is often the only method that completes with high concurrency.

    \item \textbf{Trade-offs and Recommendations.}
    If you have plenty of RAM and small data, auto or evenly-split chunking is best for speed. If you need stability and predictable memory usage, or want to handle massive volumes reliably, memaware chunking is recommended despite the slower runtime.

\end{enumerate}

Taken together, these findings highlight the importance of carefully selecting a chunking strategy based on both workload size and memory availability.
In environments where memory is scarce or the dataset is large and complex, the memaware approach offers a robust safeguard against \ac{OOM} while still delivering respectable throughput.
